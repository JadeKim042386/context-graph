Knowledge Engineering

A practical map for designing and operating concepts, relations, evidence, constraints, and change history that people and machines can reuse—not merely collecting knowledge.

Research date: 2026-09-12 Scope: ontology · knowledge graph · provenance · quality · governance · RAG Formats: text · image · video · audio Status: source-linked, evidence graded

1. Executive map

Knowledge engineering (KE) is an iterative design activity: investigate a domain, model concepts and relations explicitly, populate knowledge assets from real sources, verify consistency, provenance, and change, and connect the result to questions and work. An ontology models possible domain concepts, relations, and constraints; a knowledge graph contains real entities and assertions under that model. This distinction follows Stanford ontology guidance and the roles of the W3C RDF/OWL stack. [S1][S2][S3]

Key judgment: A good KE system is not a graph that collected the most data. It is a system that can answer what was recorded for each claim, in what meaning, from which source, when, by whom, and under which constraints.

2. Starting point: competency questions

Do not start with a tool or graph. Write down the questions the system must answer first. Questions narrow the domain boundary and determine the required classes, relations, values, and source detail. For example, “What did a design decision supersede, and which evidence and later decision followed it?” requires relations, time, and lineage beyond simple document search.

  1. Record the question's user, decision time, tolerated latency, and cost of error.
  2. Mark the entities, relations, attributes, time, and sources needed for the answer.
  3. Create answerable examples and counterexamples that must remain unanswerable.
  4. Decide whether the question belongs to a graph query, document search, rule validation, or human review.
  5. Evaluate a bounded vertical slice instead of modeling the whole domain at once.
Question: Which decision superseded ADR-42?
Required: Decision, supersedes, identifier, source document, source line, effective date
Pass: exact relation + evidence location
Fail: similarity-only match, unsupported inference, missing provenance

RDF represents a graph as subject–predicate–object triples and uses named graphs to preserve graph and source boundaries. [S2] OWL provides richer semantics, consistency checking, and inference, but maximum expressiveness is not necessary for every operational dataset. [S3] In practice, a gradual path from glossary → taxonomy → SKOS → lightweight ontology → constraints and lineage is easier to maintain.

5. Ontology engineering workflow

  1. Scope. Agree on domain boundary, users, competency questions, and non-goals.
  2. Reuse. Find existing ontologies, vocabularies, and identifiers and assess reuse or mapping. OBO Foundry emphasizes openness, shared formats, unique IRIs, versioning, clear scope and definitions, documentation, and maintenance. [S6]
  3. Terms. Collect core nouns and verbs, separating synonyms, abbreviations, and multilingual labels.
  4. Conceptualization. Decide whether each item is a class, instance, relation, or attribute.
  5. Formalization. Define URI/IRI policy, domain/range, cardinality, disjointness, and temporal semantics.
  6. Population. Extract claims and entities from documents, databases, APIs, images, video, and audio while preserving source spans and confidence.
  7. Validation. Run competency-question checks, SHACL, source comparison, entity resolution, deduplication, orphan, and conflict checks.
  8. Release and maintenance. Operate versions, change history, owners, deprecation, migration, and user feedback.

Stanford's Ontology Development 101 does not assume one correct ontology methodology; it emphasizes purpose, reuse, enumeration, definitions, hierarchy design, and iterative evaluation. [S1] Therefore competency questions and validation loops matter more operationally than the name of a methodology.

6. Quality: make each claim verifiable

Treat a knowledge-graph edge as an evidence-backed claim rather than a plain string. At minimum, store the following metadata.

  • identity: Stable IRI or canonical ID for subject and object.
  • meaning: Predicate definition, domain/range, and inverse or symmetric behavior.
  • evidence: Original URL/file, document version, citation span, and line/time offset.
  • time: Source publication time, observed time, and validity interval.
  • agent/activity: Extractor, reviewer, transformation, and approval event.
  • confidence: Store the calculation rule and review state, not only a score.
  • status: proposed, verified, disputed, deprecated, superseded.

PROV-O is a standard model for generation, use, and responsibility relations among entities, activities, and agents. [S5] It lets users ask who created a value and which transformations it passed through. Provenance is not proof of truth, so reliability rules and human review remain separate.

7. FAIR and knowledge governance

The FAIR principles guide knowledge assets to be Findable, Accessible, Interoperable, and Reusable. GO FAIR highlights persistent identifiers, rich machine-readable metadata, standard protocols, shared vocabularies, qualified references, provenance, and licenses. [S7] FAIR is not the same as open access; assets requiring access control can still meet part of the FAIR goal when metadata and access conditions are clear.

ISO 30401 treats knowledge management as a system connected to organizational goals and stakeholder needs, including leadership, culture, process, and continual improvement. [S8] Creating an ontology without an owner, review cadence, change notification, and retirement policy is not complete KE.

8. Automated extraction, entity resolution, and LLM/RAG

Automation increases acquisition speed but does not remove semantic responsibility. Automatic KG-construction research treats entity/relation extraction, coreference, entity resolution, incremental integration, provenance, and quality evaluation as separate problems. [S9][S10] Do not assume that one LLM prompt solves all of them.

  1. Split documents by stable source ID and section/chunk/timecode.
  2. Extract candidate entities and relations and store original spans.
  3. Compare candidates with canonical entities; limit automatic merge to high-precision cases.
  4. Filter structural errors with ontology domain/range and SHACL shapes.
  5. Have a person review ambiguous merges, relations, and definitions and record the decision.
  6. Record model, prompt, and ontology versions and rerun with regression fixtures.

GraphRAG can combine graph traversal with vector/text retrieval to provide multi-hop relations, global summaries, and provenance, but it introduces graph-construction cost, staleness, entity resolution, and latency. The claim that “a graph eliminates hallucination” is too strong. If the graph is wrong or contains unsupported extraction, the model can produce a more plausible wrong answer. [S9][S10]

Recommended separation: Let the vector index retrieve candidate context, the graph provide explicit relations and constraints, the original source provide final evidence, and human review handle high-impact changes.

9. Image, video, and audio knowledge engineering

Do not store multimedia as one undifferentiated file. Separate work, file, segment, observation, claim, and source. Video needs shot, scene, and timecode; audio needs speaker, utterance, timecode, and transcript version; images need region, caption, OCR, coordinates, and annotation.

Always separate “observed” from “interpreted” in multimedia claims. Seeing text in an image is an observation; deciding that it refers to a particular entity is an interpretation. Preserve title, summary, original URL, license, and validation date as text so the knowledge document survives an embed failure.

13. Minimum operating loop for this project

The current Context Graph project is a deterministic tool that copies document structure and returns questions, paths, chains, and conflicts. Therefore its KE extension prioritizes preserving source claims, line locations, explicit relations, stale maps, and conflict sidecars over allowing an LLM to guess relations.

  1. Capture: Store knowledge documents as Markdown/HTML and record terms, units, sources, and relations beside each claim.
  2. Link: Write explicit relations such as `- caused_by [[Decision]]` and `- supersedes [[Decision]]`; keep a bare `[[Target]]` as a mention.
  3. Build: Refresh the map with `build_map.py` and inspect the conflict sidecar.
  4. Ask: Use `ask.py` to ask narrowly about values, paths, explanations, chains, and conflicts.
  5. Check: Compare returned source file/line locations with the original and run deterministic builds and tests after changes.
  6. Review: Do not add facts, relations, or definitions without human approval. Make small edits and record reasons and validation results.
Practical recommendation: HTML can provide rich visual material, but the current parser excludes images, styles, and scripts from the graph and reads mainly text. Summarize key claims and sources for image, video, and audio as HTML text as well so they do not disappear from map queries.
