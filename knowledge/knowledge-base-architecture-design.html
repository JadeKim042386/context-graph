Evidence-First Knowledge Base Architecture

Status: proposed · baseline date: 2026-09-14 · evidence source: knowledge-engineering.html

1. Purpose and summary

This document is the storage and validation contract for new contributors. It explains where knowledge is stored, what shape it takes, who checks it, and how approved material reaches search.

One sentence: Preserve originals unchanged, store concepts, claims, sources, and evidence as small canonical records, then generate HTML, graph, and search projections only from reviewer-approved revisions.

A precise evidence location is a locator; collection and change history is provenance; a durable record name is a stable ID; and a connection between records is a graph edge. A URL or response check without body verification is metadata-only. A fixed input set for one build is a snapshot. Unresolved or unverifiable knowledge is recorded as abstain.

2. Architecture overview

Original material stays unchanged. Small JSON records describe it, evidence connects it to claims, a reviewer approves or rejects the connection, and only approved records are used for search and answers.

Immutability: Never overwrite an approved Claim. Create a new Claim and link the old one with supersedes, deprecated, or retracted. Follow Web Annotation Target/Selector semantics and bind every target to Source revision and hash. Connect collection, transformation, and review with PROV-O.

6. Fields and lifecycle

Allowed statuses are draft, candidate, under-review, accepted, conditional, deprecated, retracted, stale, and abstain. Scores are normalized to [0,1]; missing values remain missing.

For an update, create a new revision, preserve the prior revision and reason, connect supersedes, mark dependent conclusions stale, validate the staging projection, and switch the active revision atomically.

7. Locator and reproducibility rules

Text uses quote/position or HTML selector; tables use sheet/table/row/column; PDFs use revision/page/bounding box; images use hash and xywh or SVG; video/audio use hash and start/end timecode; structured data uses dataset version, query, and row/slice; code uses revision, path, line, and test run. Always retain Source revision and content hash.

8. Source boundaries and projections

RDF and JSON-LD projections may be generated from the canonical graph. Source collections can be described with DCAT 3. Every projection records input revision/hash and generation activity. If projections disagree, validate the canonical graph and regenerate the affected projection.

Metadata-only external observations are not content evidence. A URL with a status code but no body, locator, or content hash remains unknown and may produce only abstain. Rights are verified only from explicit rights evidence.

Normalize a question's target, relation, scope, date, and output format; search approved records; build a minimal Context Pack; reproduce every locator; then return answer, conflict, or abstain.

11. Operations and glossary

Read the L5 index first and open only the required L3/L2 records. Every ingest, query, review, and rebuild appends to the provenance log. Lint checks orphan records, broken locators, stale dependencies, hidden conflicts, and projection drift.

Canonical record
The stable, format-neutral record used as the source for projections.
Projection
A generated representation such as HTML, Markdown, PDF, RDF, JSON-LD, graph JSON, or a search index.
Context Pack
The smallest evidence-backed input bundle needed to answer one question.
Abstain
A deliberate decision not to assert an answer because evidence is missing, stale, conflicting, or not reproducible.

Answer rule: Answer only when scope is clear, the Claim is approved, direct Evidence and Source revision exist, the locator reproduces, and no unresolved conflict changes the result.
